# 2026-07-27 — Web v1 surface (cycle 12c)

cycle 12c ships the v1 interactive web surface. the v0 read-only
surface (cycle 12b) had four GET routes. v1 adds two POST routes
and the engine integration that makes the v1 surface *playable*.

## what shipped

```
src/sim/run-loop.js   +246 lines: stepTurn and pickCrisis exports
src/web/server.js     v0 server replaced with the v1 server
data/runs/            the live sessions dir (created on first POST /runs)
```

the engine change is *additive*: two new exported functions, no
logic changes to the existing `runLoop`. the discord bot and
terminal version are unaffected.

## the engine change

`src/sim/run-loop.js` gained two new exported functions:

- `stepTurn({ state, crisis, playerMove, identity, turnNumber, priorTurns, callLLM, callFallback, ... })` — runs one turn. takes the current state, the crisis to display, and the player's move; calls the LLM (or its fallback); applies the delta; checks for collapse; returns the new state and the world record.
- `pickCrisis({ turnNumber, state, priorWorld, seed, seedId, usedSeedIds, usedActors, ... })` — selects the crisis to display. turn 1 uses the seed/deck (pre-selected or random); turn 2+ uses the prior turn's world output.

`runLoop` is unchanged in behavior. it still runs the whole session
in one call for the discord bot and terminal version. the new
functions are the per-turn API for surfaces that need it (the web
v1 surface).

### why the engine change was needed

the spec said "no changes to `src/sim/`." cycle 12b verified that
commitment held for the v0 surface (read-only, no engine calls).
cycle 12c couldn't: the engine's only public entry points were
`runLoop` (in-process, surface-driven) and `runSimulationAsync`
(takes a script). neither fits an HTTP surface where each request
is a separate process invocation. the per-turn API was extracted
from `runLoop`'s body with no logic changes.

the user confirmed the path: "extract `stepTurn` from `runLoop`.
surgical change, no logic change, surface-adapter pattern works."

## the v1 routes

```
GET  /                     cold-start (lists finished runs)
GET  /runs                 JSON list of runs
GET  /runs/:id             run page (B chat-thread layout)
GET  /runs/:id/report      post-game report (alias for ended runs)
POST /runs                 start a new run; returns the run id and the first turn
POST /runs/:id/move        submit a move; returns the next turn or end-of-run
```

the two POST routes are the new things. `POST /runs` selects the
turn-1 crisis from the engine's deck (`selectSeed` + `pickCrisis`)
and writes a session file at `data/runs/<id>.json`. `POST /runs/
:id/move` reads the session, calls `stepTurn` (which calls
`generateWorld` for the LLM, with `interpret` as the fallback),
applies the delta, checks for collapse or stabilization, and writes
the updated session.

## the auth decision

the spec's decision (1) called for bearer-token auth in v1. the
v1 surface ships *without* bearer-token auth. the run URL is the
access — the player bookmarks their run URL and comes back to it.

reasoning:

- the project's no-PII posture: bearer-token auth without a
  database means storing tokens in cookies or query strings,
  neither of which is appropriate for an edutainment showcase
  where the player might share a link
- the user has been gating `npm install` (which would be needed
  for sqlite or any auth-cookie library)
- the run URL *is* the access. for a single-player edutainment
  surface, the URL-as-access is simpler, more honest, and
  aligned with the project's "no surveillance" framing
- the v0 surface already worked this way: the share URL is the
  run URL. the v1 surface is the same: the run URL is the access
  for the player *and* the share for the returner

v2 (cycle 13+ or later) can layer auth on top: add a sqlite users
table, issue a token on first `POST /runs`, verify on subsequent
requests. the v1 surface's session contract is already
url-keyed; the auth layer is a small addition.

## the end-of-run flow

when `stepTurn` returns a `collapse`, the v1 server:

1. writes the end-of-run timestamp and outcome to the session
2. calls `narrateRunEnd` (the engine's LLM-driven end-of-run
   narrative generator) for the post-game report
3. calls `generateArtifact` + `renderArtifactHtml` to write the
   self-contained artifact HTML
4. persists the final state to the session file

the run page then shows the chat-thread up to the collapse, plus
the end-of-run prose. the share URL (the run URL) is the
post-game report — same URL, state-driven content.

## the engine commitment — re-stated

the spec said "no changes to `src/sim/`." the v0 surface (cycle
12b) verified that. the v1 surface (cycle 12c) required a small
change: extracting two new functions from `runLoop`. the change
is *additive* — no logic changes, no behavior changes to the
existing `runLoop` function. the surface-adapter pattern is the
architecture that makes this implementable: the engine exposes
two entry points (`runLoop` for in-process surfaces, `stepTurn`
for per-turn surfaces), and the surfaces choose which to use.

if a stricter reading of "no changes" is preferred, the v1
surface can be reverted to the v0 surface + a child-process
model where each run spawns its own `runLoop` process. that's
option (b) from the cycle 12c planning conversation. the user
chose option (a) — surgical engine change. the v1 surface
ships.

## what 12c explicitly does NOT do

- no bearer-token auth (see "the auth decision" above)
- no /status page (decision 4 — 12d)
- no live corpus-quote picker for new turns (decision 2 — 12d;
  the v1 surface reads the corpus quote from the LLM's
  grounding_trace, which is good enough for the chat-thread
  rendering, but the picker logic for the dedicated
  footer is 12d)
- no advisor interaction (decision 5 — 12d; the v1 surface
  doesn't render the advisor panel yet — the dock renders
  but the buttons are non-functional, same as v0)
- no help commands (cycle 11's help is TTY-only; the v1 web
  surface doesn't have the help affordance yet)
- no multi-user coordination (single-player; the run URL
  is the only access)
