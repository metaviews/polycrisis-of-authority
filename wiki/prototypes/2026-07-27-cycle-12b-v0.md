## architecture

**4 routes, no auth, no write paths, no LLM call, no database.**

```
GET /                          cold-start (frame + finished-runs list)
GET /runs                      JSON list of runs (machine-readable mirror)
GET /runs/:id                  run page (B chat-thread layout)
GET /runs/:id/report           post-game report (alias for ended runs)
```

`src/web/server.js` reads JSON from `data/seed-runs/*.json` and
`runs/*.json` (real simulation runs) at request time, hands the
data to `src/web/surface.js`, which renders the chat-thread HTML.
no in-memory state, no caching, no write paths.

## the surface-adapter pattern (engine commitment)

`src/web/surface.js` is modeled on `src/bot/surface.js` — the
discord surface adapter that shipped in cycles 6a-6f. same shape:
the surface consumes JSON-shaped engine data and emits HTML. the
engine doesn't know which surface is consuming it.

`src/web/` does not import from `src/sim/`. the engine commitment
(no changes to `src/sim/`) holds. the surface-adapter pattern is
the architecture that makes this implementable.

## the cold-start shape

**option (b) from the cycle 12a question** — the cold-start lists
finished runs + frame paragraph + v0 note. no fake "start a run"
button. honest about v0 being read-only. the run-start button
appears in 12c when the v1 surface lands.

the frame paragraph is the spec's one-paragraph description of

runs you can read."

## decisions made during 12b implementation

1. **node's built-in `http`, not express.** no `npm install` was
   needed. the v0 surface has 4 routes with no middleware, no
   async, no DB — `http.createServer` is enough. this matches
   the project's "no framework churn" principle. express is
   still a candidate for 12c+ if async middleware becomes
   useful, but v0 ships with zero new dependencies.

2. **read-only decision dock is rendered for active runs.**
   `src/web/surface.js` renders the dock with a `disabled`
   textarea and submit button when `isActive: true`. the
   `v0 is read-only` note is in the dock. active runs
   in v0 don't have a way to be created (no run-start
   yet) but the code path is in place for 12c.

3. **report alias is byte-identical to the run page for
   ended runs.** the spec said `GET /runs/:id/report` is the
   share URL. the v0 surface serves the same content as
   `GET /runs/:id` for `state='ended'` runs. if a self-
   contained artifact HTML exists at `runs/<id>-artifact.html`,
   that file is served as-is; otherwise the run page is
   rendered with the end-of-run prose. both paths land on
   the same chrome.

4. **seed runs are committed, real runs are read at request
   time.** this matches the discord bot's pattern of having
   committed test fixtures alongside the real runtime data.
   the seed runs are stable across cycles; the real runs
   depend on what the simulation has actually been played.

## the post-game share model (resolved during 12b)

per the chat-thread direction B + decision 3 (a): the share URL
is `GET /runs/:id` with state-driven content. `state='active'`
renders the per-turn page (placeholder in v0). `state='ended'`
renders the same surface with the end-of-run prose appended
(this is what 12b ships). one render path, one URL. the report
alias `/runs/:id/report` exists for compatibility with the
spec's "post-game report" decision but serves the same content
in v0.
